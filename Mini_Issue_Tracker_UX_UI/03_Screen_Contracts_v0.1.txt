# Mini Issue Tracker: Developer-Verifiable Screen Contracts

Статус документа: робочий контракт для перевірки дизайну, прототипу та реалізації. Не затверджений.

Контракти спираються на `SD_Spec.docx` і погоджений Decision Log D-01–D-08. Межі Release MVP: US-01–US-08. US-09 (attachments) не включено; SR-10/SR-11 (автоматична категоризація та рекомендація пріоритету) залишаються Future/Deferred.

Щоб розробник не мусив вгадувати, що саме автор мав на увазі, нижче розділено три рівні:

- SOURCE: прямо випливає з вимог або погодженого D-ID.
- PROPOSED D-ID: потрібна деталізація для перевірки, якої джерела не визначають. Це пропозиція, а не нова продуктова вимога.
- Verification level: `Mockup` перевіряє наявність і розміщення елементів; `Prototype` перевіряє демонстраційні переходи й видимі реакції; `Implementation` перевіряє реальні дані, права, збереження та бізнес-правила.

Для прототипу погоджено mock data і заздалегідь визначені результати (D-08). Тому успішна демонстрація прототипу не доводить, що дані справді збережено або права забезпечено сервером. Майбутній макет також не отримує PASS просто за факт свого існування.

## 1. Permission matrix

`Assignee` — це відношення конкретного користувача до конкретного issue, а не окрема глобальна роль. Права на зміну статусу залежать від цього відношення, а не від посади Team Lead.

| Дія             | Team Member, non-assignee | Team Member, assignee              | Team Lead, non-assignee | Team Lead, assignee                |
| --------------- | ------------------------- | ---------------------------------- | ----------------------- | ---------------------------------- |
| View            | Дозволено                 | Дозволено                          | Дозволено               | Дозволено                          |
| Create          | Дозволено                 | Дозволено                          | Дозволено               | Дозволено                          |
| Comment         | Дозволено                 | Дозволено                          | Дозволено               | Дозволено                          |
| Assign          | Заборонено                | Заборонено                         | Дозволено               | Дозволено                          |
| Change priority | Заборонено                | Заборонено                         | Дозволено               | Дозволено                          |
| Change status   | Заборонено                | Дозволено, лише дозволений перехід | Заборонено              | Дозволено, лише дозволений перехід |

Джерела: BR-01, BR-02, BR-06, BR-08/BR-08.1; US-03, US-04, US-06, US-07; D-05, D-06.

За D-05 недоступні за роллю елементи показуються disabled, а не приховуються. Для статусу діють дві незалежні умови: користувач має бути assignee, і перехід має бути дозволений BR-08.1. Team Lead без призначення не отримує права змінювати статус автоматично.

## 2. Повна матриця status transitions

Дозволено тільки чотири переходи з BR-08.1. Перебування в поточному статусі не є переходом. Закритий issue не має вихідних переходів.

| Поточний статус | Open           | In Progress    | Resolved       | Closed         |
| --------------- | -------------- | -------------- | -------------- | -------------- |
| Open            | Немає переходу | Дозволено      | Заборонено     | Заборонено     |
| In Progress     | Заборонено     | Немає переходу | Дозволено      | Заборонено     |
| Resolved        | Заборонено     | Дозволено      | Немає переходу | Дозволено      |
| Closed          | Заборонено     | Заборонено     | Заборонено     | Немає переходу |

Усього є 12 комбінацій між різними статусами: 4 дозволені? Ні, саме 4 дозволені, а решта 8 заборонені. Діагональні клітинки не є переходами й не входять до цих 12.

### Що це означає для контролу статусу

- Доступний вибір має відображати лише допустимі наступні статуси для поточного статусу.
- Якщо прототип або макет показує інші значення, це дефект відповідності контракту.
- Якщо користувач не є assignee, контрол зміни статусу показується disabled за D-05.
- Перехід `Resolved → In Progress` дозволений. `Resolved` не означає `Closed`.
- Після `Closed` статус більше не змінюється.

Важливе розділення рівнів: макет може показати disabled-стан або набір опцій; прототип може імітувати вибір і Apply; лише реалізація може довести, що невалідний перехід справді відхиляється на рівні бізнес-логіки, а збережений статус залишається незмінним.

## 3. Important predicate

Точна умова належності до Important:

`priority ∈ {High, Critical} AND status != Closed`

| Priority              | Status      | Очікувана належність до Important |
| --------------------- | ----------- | --------------------------------- |
| High                  | Resolved    | Так                               |
| Critical              | Closed      | Ні                                |
| Відсутній (`Not Set`) | Open        | Ні                                |
| Low                   | Open        | Ні                                |
| Normal                | In Progress | Ні                                |
| Critical              | In Progress | Так                               |

Це відповідає AC-08.1–AC-08.4 та BR-09/BR-09.1. Попри назву User Story View Important Open Issues, формальна умова виключає лише `Closed`, а не `Resolved`. Контракт не підміняє правило заголовком історії.

`Not Set` означає, що priority відсутній, а не що він дорівнює `Low`. Під час створення issue priority не встановлюється (AC-01.5, BR-03–BR-05, D-03).

## 4. Screen contracts

### S-01. Authentication boundary

Тип: службова annotation / boundary, не продуктовий екран входу.

- Призначення: позначити, що доступ до S-02 передбачає автентифікованого користувача.
- Actors: Team Member, Team Lead.
- Entry condition: відкриття демонстрації.
- Visible data: немає полів форми, повідомлень входу або реального профілю. У документації можна показати annotation: «Demo starts authenticated».
- Controls: немає.
- Default / empty / validation / error: не визначені, бо S-01 не є формою входу.
- Incoming: старт демонстрації.
- Outgoing: до S-02-A, S-02-B або S-02-C залежно від підготовлених mock data і вибраного стану.
- Source/D-ID: BR-01; D-02, D-08.
- Mockup: перевірити, що S-01 позначений як boundary/annotation, а не намальований як login screen.
- Prototype: перевірити, що демо починається в автентифікованому контексті.
- Implementation: автентифікація, сесія та захист доступу не покриваються цією annotation; їх треба перевіряти окремо.

### S-02-A. Issues List, вкладка All

Тип: screen/state.

- Призначення: показати список зареєстрованих issues.
- Actors: Team Member, Team Lead.
- Entry conditions: користувач уже автентифікований; список містить хоча б один issue або стан використовується як основний список.
- Visible data:

| Поле     | Обов’язковість                                                   | Вигляд відсутнього значення                             |
| -------- | ---------------------------------------------------------------- | ------------------------------------------------------- |
| ID       | Так, для кожного issue                                           | Відсутність ID є дефектом даних                         |
| Title    | Так                                                              | За AC-01.2 має бути непорожнім                          |
| Status   | Так                                                              | Відсутність статусу є дефектом даних                    |
| Priority | Поле має бути представлене в рядку; значення може бути відсутнім | `Not Set`                                               |
| Assignee | Лише якщо призначений                                            | `Unassigned` — PROPOSED D-ID, бо точний текст не задано |

Список має відображати ID, Title, Status, Priority та Assignee, якщо він призначений (AC-02.2). Статус у списку окремо вимагає AC-05.1 і AC-05.3.

Controls

| ------- | ----------------- | ----------------------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------ | --------------------- |
| C-02-01 | All               | Tab                                                         | Видимий; enabled                                              | Click → S-02-A                             | D-01                  |
| C-02-02 | Important         | Tab                                                         | Видимий; enabled                                              | Click → S-02-B                             | D-01, AC-08.1–08.4    |

Default state: All активна; список містить issues. Це базовий стан демонстрації, а не вимога щодо сортування чи порядку рядків.

Empty state: якщо зареєстрованих issues немає, показати S-02-C (AC-02.5). Точний текст порожнього стану не визначено.

Validation / error: немає спеціального list-validation state у джерелах. Поведінка помилки завантаження списку не визначена.

Incoming transitions: T-01, T-03, T-06, T-07, T-20, T-21, T-22, T-23, T-24, T-25, T-26 згідно з таблицею переходів нижче.

Outgoing transitions: T-02, T-05, T-08, T-09, T-10, T-11.

Verification:

- Mockup: назви вкладок, видимі поля списку, активна вкладка, кнопка Create issue, вибір рядка.
- Prototype: All/Important navigation, відкриття деталей, відкриття Create modal, повернення до попередньої вкладки.
- Implementation: фактичне отримання списку, коректність даних, правила прав доступу, формування списку й відповідність Important predicate.

### S-02-B. Issues List, вкладка Important

Тип: screen/state того самого S-02, не окрема сторінка.

- Призначення: показати issues, що відповідають Important predicate.
- Actors: Team Member, Team Lead.
- Entry conditions: автентифікований користувач обирає вкладку Important.
- Visible data: ті самі поля, що й у S-02-A: ID, Title, Status, Priority, Assignee за наявності.
- Controls:

| C-ID    | Label             | Type     | Visible / enabled                           | Trigger → результат       | Source/D-ID        |
| ------- | ----------------- | -------- | ------------------------------------------- | ------------------------- | ------------------ |
| C-02-01 | All               | Tab      | Видимий; enabled                            | Click → S-02-A            | D-01               |
| C-02-02 | Important         | Tab      | Видимий; активний                           | Click → лишитися в S-02-B | D-01               |
| C-02-03 | Create issue      | Button   | Видимий; enabled для обох типів користувача | Click → M-01              | US-01, BR-02, D-01 |
| C-02-04 | Issue row / title | Row/link | Видимий для кожного результату              | Select → S-03             | AC-02.3            |

Default state: активна вкладка Important, список сформований за формальним predicate.

Empty state: якщо жоден issue не відповідає predicate, показати порожній стан на цій вкладці. Окремий дизайн такого стану не визначений; його текст і чи відрізняється він від S-02-C є питанням бізнес-рішення.

Validation / error: відхилені priority/status зміни мають не створювати змінений стан issue; точне повідомлення про помилку зміни не визначене джерелом.

Incoming: T-02, T-08, T-09, T-10, T-11, T-20, T-21, T-22, T-23, T-24, T-25, T-26 — якщо попереднім list state була Important.

Outgoing: T-02, T-05, T-08, T-09, T-10, T-11.

Verification:

- Mockup: Important є вкладкою в тому самому list screen; видимі колонки узгоджені з All.
- Prototype: перехід на вкладку й відображення заздалегідь підготовлених відповідних mock issues.
- Implementation: фільтрація за `priority ∈ {High, Critical} AND status != Closed`, включно з High + Resolved і виключенням Closed незалежно від priority.

### M-01. Create Issue modal

Тип: modal/overlay, не самостійна сторінка.

- Призначення: створити issue з Title та Description.
- Actors: Team Member, Team Lead.
- Entry conditions: автентифікований користувач активує Create issue у S-02.
- User-entered fields:

| Поле        | Обов’язкове   | Початкове значення | Валідація / відсутнє значення                                                                           |
| ----------- | ------------- | ------------------ | ------------------------------------------------------------------------------------------------------- |
| Title       | Так (AC-01.2) | Порожнє            | Порожній Title блокує створення; джерело містить текст `Title is required` у Gherkin-сценарії для AC-02 |

Автоматично задані після успішного створення:

| Поле       | Очікуване значення                    | Джерело                    |
| ---------- | ------------------------------------- | -------------------------- |
| ID         | Новий унікальний ID                   | AC-01.4                    |
| Status     | `Open`                                | AC-01.4, AC-07.1, BR-03    |
| Author     | Поточний користувач                   | AC-01.4                    |
| Created at | Час створення                         | AC-01.4                    |
| Priority   | Відсутній, у UI показується `Not Set` | AC-01.5, BR-03–BR-05, D-03 |
| Assignee   | Відсутній після створення             | D-04                       |

ID, status, author, created_at, priority та assignee не є користувацькими полями форми. Не додавати в Create modal контролів для їх ручного встановлення.

| ------- | -------------- | ----------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------- | ------------- |

Default state: обидва поля порожні. Пріоритет не відображається як вибір у формі.

Validation states:

- Title порожній: issue не створюється; показати `Title is required` згідно з Gherkin-прикладом.
- Description порожній: issue не створюється (AC-01.3); точний текст і формат повідомлення — PROPOSED D-ID.
- Обидва поля порожні: мають бути виконані обидві обов’язкові умови; чи показувати два повідомлення одночасно, джерело не визначає.

Error states: помилка збереження issue та її текст не описані в AC-01. Для макета не вигадувати backend error. У прототипі можливий лише явно позначений демонстраційний результат, не доказ реалізації.

Outgoing: T-06 після успіху; T-07 після валідаційної відмови; T-04 для закриття modal, якщо буде погоджено Cancel/Close. Повернення на попередню вкладку після закриття має зберігати list state за D-07.

Verification:

- Mockup: лише два користувацькі поля, required-ознаки, кнопка Create, відсутність priority/assignee/status controls.
- Prototype: спроба створення, видима валідація, закриття modal і повернення на попередню вкладку; результат створення використовує mock data.
- Implementation: унікальність ID, реальне збереження, автоматичні поля, відхилення невалідного вводу, відсутність запису при невдалому створенні.

Default state: відображаються всі поля issue, доступні керування відповідно до ролі/assignee, список коментарів і поле нового comment. Поточні значення не змінюються лише від відкриття деталей.

Priority states:

- Відсутній priority показується як `Not Set`.
- Допустимі значення, які можна встановити: `Low`, `Normal`, `High`, `Critical`.
- Окремої команди для скидання priority немає (D-03).
- `Not Set` є відображенням відсутнього значення, а не п’ятим значенням, яке можна встановити.

Assignment states:

- Без призначення: assignee відсутній; після створення це очікуваний стан (D-04).
- Team Lead може призначити одного assignee, який є членом команди; поточний assignee має бути видимим (US-03, чотири вихідні ненумеровані acceptance criteria).
- Team Member бачить керування disabled, а не приховане (D-05).

Status states:

- Статус завжди відображається (AC-05.2).
- Team Member/Team Lead, які не є assignee, не можуть його змінити (AC-07.4, BR-08).
- Team Lead без призначення також бачить disabled-контрол.
- Вихідні переходи з `Closed` відсутні.

Comment states:

- Порожній comment не створюється (AC-06.1).
- Після успішного збереження comment показується з author і creation date/time (AC-06.2–06.4).
- Після невдалого збереження comment не додається, а користувач бачить error (AC-06.5).
- Точний текст error і правила повторного submit не визначені джерелом.

Incoming: T-08, T-09, T-10, T-11, T-12–T-26 залежно від дії та результату.

Outgoing: T-03, T-12–T-26; T-03 повертає користувача до list tab, який був активним перед відкриттям деталей.

Verification:

- Mockup: видимі поля issue; блоки assignment, priority, status і comments; disabled-стани для неуповноважених користувачів; `Not Set`; comment author/time; помилка збереження як окремий компонентний стан.
- Prototype: демонстрація selector → Apply, допустимих status transitions, comment success/error, переходу до Important/All і повернення до попередньої вкладки.
- Implementation: реальні права, збереження assignment/priority/status/comment, заборона недопустимих status transitions, незмінність даних при помилці збереження, фактичні author/time і застосування Important predicate.

- D-06: для assignment, priority і status застосовується схема selector → Apply; після успішної зміни лишаємося на S-03.
- D-07: повернення з деталей зберігає попередню вкладку списку.
- D-08: прототип використовує mock data і заздалегідь визначені outcomes, без реального login/database.

## 9. Межі перевірки

Цей контракт дозволяє перевірити, чи дизайн показує потрібні дані та controls, чи демонструє прототип очікувані переходи й чи не порушує видимі правила доступу. Він не доводить:

- реальну автентифікацію та захист доступу;
- збереження даних після перезапуску;
- унікальність ID на рівні сховища;
- серверну перевірку дозволів для assignment, priority, status і comments;
- атомарність невдалого збереження comment;
- фактичну відповідність даних predicate Important;
- NFR-01 (response time < 1 s), NFR-03 (HTTPS only) і NFR-04 (backup);
- поведінку API при недоступності мережі, якщо вона не буде окремо визначена.

Підсумок: мінімальна продуктова система залишається такою: S-01 boundary annotation, S-02 зі станами All / Important / Empty, M-01 Create modal і S-03 Issue Details. Assignment, priority, status і comments не перетворюються на окремі сторінки. Усі нові деталі UX позначені як `PROPOSED D-ID`; вони не змінюють межі MVP і не є джерельними вимогами.
