# Mini Issue Tracker: Figma Design Implementation Brief

## 1. Purpose and Scope

Create an editable, grayscale, low-fidelity Figma design for the Mini Issue Tracker based on the approved Screen Contracts and Decision Log.

The design must communicate the canonical screens, required issue information, role-based control availability, status transitions, Important Issues filtering, and key empty/error states. It is a design artifact for review, not a new UX proposal or a complete product specification.

Cover the approved screen system:

- `S-01` — Authentication Boundary
- `S-02-A` — All Issues
- `S-02-B` — Important Issues
- `S-02-C` — Empty Issues List
- `M-01` — Create Issue Modal
- `S-03` — Issue Details

Create the canonical screens and compact examples of control states. Do not duplicate entire screens for every combination of role, assignee, priority, and status.

Source references: `SD_Spec.docx`, §§ 2, 3, 5, 8; `D-01`–`D-08`.

## 2. Design Constraints

- Use desktop grayscale low-fidelity styling. Do not introduce a color system, decorative visual language, or polished high-fidelity UI.
- Use editable, native Figma layers rather than flattened screenshots or image-based mockups.
- Create reusable local components for repeated elements such as issue rows, status labels, priority labels, fields, buttons, and permission states.
- Use Auto Layout where appropriate for layouts, rows, forms, dialogs, and reusable components.
- Use meaningful, consistent layer and component names. Preserve the canonical screen IDs exactly.
- Keep all canonical screens and supporting references on one working page.
- Place explanatory notes, source references, blockers, and transition annotations outside product frames. Do not present design documentation as part of the product UI.
- Do not create page-icon placeholders, decorative squares, row-selection controls, or bulk-action controls.
- Use consistent spacing and alignment sufficient to communicate hierarchy and interaction intent. No precise spacing scale, typography system, or responsive behavior is prescribed by this brief.

Approved decisions: `D-01`, `D-05`, `D-06`, `D-08`.

## 3. Canonical Screens and States

### `S-01` — Authentication Boundary

Represent the authentication boundary as a clearly labeled annotation, not as a designed login page.

The prototype walkthrough begins in an authenticated state at `S-02`. Do not create login or registration flows.

Approved decision: `D-02`.

### `S-02-A` — All Issues

Design the main issue list with an All tab selected.

Each issue row must display:

- Issue ID
- Title
- Status
- Priority
- Assignee, when assigned

Rows must provide a clear way to open the corresponding issue details.

Include a Create Issue entry point that opens `M-01`.

Use the same list structure and issue-row component in `S-02-B`.

Source references: `AC-02.1`–`AC-02.3`, `AC-02.5`; `D-01`.

### `S-02-B` — Important Issues

Use the same list structure as `S-02-A`, with the Important tab selected.

Display only issues that satisfy the approved Important predicate defined in Section 7.

The selected tab must be visually distinguishable in grayscale without relying on color.

An empty Important result is a state within `S-02-B`, not an additional canonical screen.

Source references: `AC-08.1`–`AC-08.4`; `BR-09`, `BR-09.1`; `D-01`.

### `S-02-C` — Empty Issues List

Represent the empty state when there are no registered issues.

The state must make it clear that the list contains no issues. Do not invent additional onboarding content, illustrations, or secondary actions.

Source reference: `AC-02.5`.

BLOCKER B-01: The exact empty-state wording and the distinction in presentation between an entirely empty All list and an empty Important result have not been approved. Keep the state structure minimal and annotate the unresolved copy/presentation decision outside the product frame. Do not treat the empty Important result as a new canonical screen.

### `M-01` — Create Issue Modal

Create a modal over the issue-list context.

Required fields:

- Title — required text field
- Description — required text field or multiline field

Include a Create action.

A newly created issue receives:

- A unique ID
- Status `Open`
- The current user as author
- A creation timestamp
- Priority `Not Set`
- No assignee

Do not add a priority selector or assignee selector to the creation modal.

Source references: `AC-01.1`–`AC-01.5`; `BR-02`–`BR-05`; `D-03`, `D-04`.

BLOCKER B-02: The modal's Cancel/Close behavior and the destination after successful creation have not been approved. Do not invent navigation or dismissal behavior. Annotate these as unresolved decisions outside the frame.

BLOCKER B-03: The source explicitly specifies `Title is required` for empty-title validation. It requires Description, but the exact Description validation message and the precise presentation of validation feedback are not approved. Preserve the exact Title message where represented; annotate the unresolved Description feedback rather than inventing copy.

### `S-03` — Issue Details

Display the selected issue's details, including:

- ID
- Title
- Description
- Status
- Priority
- Assignee, when assigned
- Author
- Created at

Include the comments section with comment text, author, and creation date/time. Include a non-empty comment input and a comment submission control.

Include assignment, priority, and status controls as applicable to the actor's role and assignment relationship. Keep unauthorized controls visible but disabled.

For assignment, priority, and status changes, use the approved select → Apply interaction pattern. After a successful change, the user remains on `S-03`.

Provide a way to return to the previous list context. Returning from details must preserve the previously selected list tab.

Do not add issue deletion or a user-facing change-history section.

Source references: `AC-02.3`, `AC-02.4`, `AC-03` acceptance criteria, `AC-04.1`, `AC-04.2`, `AC-05.1`–`AC-05.3`, `AC-06.1`–`AC-06.5`, `AC-07.1`–`AC-07.5`; `BR-06`–`BR-08.1`, `BR-10`, `BR-11`; `D-03`–`D-07`.

BLOCKER B-04: The exact label for an absent assignee is not approved. Do not silently adopt `Unassigned` or another label as a finalized product decision. Show the unassigned condition clearly and annotate the missing label decision outside the frame.

BLOCKER B-05: Exact comment-empty validation text, failed-comment-save error text, and failed-Apply error presentation have not been approved. Show compact, clearly labeled examples of these error states, but mark their exact copy and presentation as unresolved. Do not imply that a failed comment save creates or displays a persisted comment.

BLOCKER B-06: The display format and timezone convention for creation and comment timestamps have not been approved. Include the required timestamp fields without presenting an invented format or timezone as an approved rule.

## 4. Required Labels and Data

Use the following exact status labels:

- `Open`
- `In Progress`
- `Resolved`
- `Closed`

Use the following exact priority values:

- `Not Set`
- `Low`
- `Normal`
- `High`
- `Critical`

`Not Set` represents an absent priority value. It is not an additional settable priority and must not be represented as `Low`. No priority-reset action is available.

Use the following role labels:

- `Team Member`
- `Team Lead`

Use `Assignee` for the responsible team member and `Author` for the issue creator. These are different roles in the issue data and must not be conflated.

Required issue information in the list and details is defined in the canonical screen contracts above. Do not add unrelated fields such as categories, attachments, due dates, estimates, or activity history.

Source references: `AC-02.2`, `AC-02.4`, `AC-03`, `AC-04.1`, `AC-07.2`; `BR-03`–`BR-07`; `D-03`, `D-04`.

## 5. Controls and Permissions

Permission differences must be communicated through enabled and disabled controls, not by hiding unauthorized controls.

| Control         | Team Lead                                                                                      | Team Member                                                                                    |
| --------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Create Issue    | Enabled                                                                                        | Enabled                                                                                        |
| Change assignee | Enabled                                                                                        | Disabled                                                                                       |
| Change priority | Enabled                                                                                        | Disabled                                                                                       |
| Change status   | Enabled only when the actor is the issue's assignee and a permitted outgoing transition exists | Enabled only when the actor is the issue's assignee and a permitted outgoing transition exists |
| Add comment     | Enabled                                                                                        | Enabled                                                                                        |

For assignment, priority, and status, show a selection control followed by an adjacent Apply action. A successful change keeps the user on `S-03`.

The assignee must be a team member. Only one assignee may be selected. A new issue starts without an assignee, and a Team Lead can assign or reassign it.

A Team Lead who is not the issue's assignee must not receive permission to change its status merely because of the Team Lead role.

For a status with no permitted outgoing transitions, show the status control as disabled. This includes `Closed` for every role and assignment context.

Source references: `AC-03`, `AC-04.2`, `AC-07.4`; `BR-02`, `BR-06`, `BR-08`; `D-04`, `D-05`, `D-06`.

## 6. Status Transitions

Use only the following permitted transitions:

| Current status | Permitted next status   |
| -------------- | ----------------------- |
| `Open`         | `In Progress`           |
| `In Progress`  | `Resolved`              |
| `Resolved`     | `Closed`, `In Progress` |
| `Closed`       | None                    |

All other transitions are forbidden. The status control is enabled only when the actor is the issue's assignee and the current status has a permitted outgoing transition.

Represent the available options and disabled states in compact component/state examples. Do not create a full page for every status and role combination.

Source reference: `BR-08`, `BR-08.1`; `AC-07.2`–`AC-07.5`.

## 7. Important Predicate

An issue belongs in Important Issues if and only if:

`priority ∈ {High, Critical} AND status != Closed`

Consequences that must be reflected in the design examples:

- `High` + `Open` → included.
- `Critical` + `In Progress` → included.
- `High` + `Resolved` → included.
- `Critical` + `Closed` → excluded.
- `Low` or `Normal`, regardless of status → excluded.
- `Not Set` → excluded.

`Resolved` does not mean `Closed`. A High- or Critical-priority issue remains Important while its status is `Resolved`.

Do not use the story name “Important Open Issues” to override the explicit predicate above.

Source references: `AC-08.1`–`AC-08.4`; `BR-09`, `BR-09.1`; `D-01`, `D-03`.

## 8. Required Empty and Error Examples

Provide compact component or state examples, not additional full-page screens, for the following cases:

1. No registered issues: `S-02-C`, showing an empty All list.
2. No Important results: the empty-result state within `S-02-B`.
3. Missing Title: use the source's exact message, `Title is required`. The issue must not be created.
4. Missing Description: show that creation is blocked, but mark the exact validation message as unresolved.
5. Empty comment: show that an empty comment cannot be submitted. Mark exact validation copy as unresolved.
6. Failed comment save: show an error state and no newly persisted comment. Mark exact error copy as unresolved.
7. Unauthorized control: show a visible, disabled assignment or priority control for a Team Member.
8. Unauthorized status change: show a visible, disabled status control when the actor is not the assignee, including a Team Lead who is not the assignee.
9. No outgoing status transition: show the disabled status control for `Closed`.
10. Failed Apply: provide a compact annotation/state example indicating a failed change without implying success. Exact feedback presentation remains unresolved.

Do not invent additional error messages, success notifications, modal behavior, or empty-state copy.

Source references: `AC-01.2`, `AC-01.3`, `AC-02.5`, `AC-06.1`, `AC-06.5`, `AC-07.4`; `D-05`, `D-06`.

## 9. Navigation Intent

Use these navigation intentions as annotations for the prototype walkthrough:

- `S-01` → authenticated entry at `S-02`.
- `S-02-A` → `M-01` when Create Issue is activated.
- `S-02-A` or `S-02-B` → `S-03` when an issue is opened.
- `S-03` → the previously active list tab when returning from details.
- Successful assignment, priority, or status change → remain on `S-03`.

The list tabs switch between All and Important. The empty Important state remains within `S-02-B`.

For this step, add transition annotations only. Do not build a functioning prototype, implement conditional logic, or simulate permission enforcement in code. Do not infer modal cancellation or successful-creation destinations that have not been approved.

Approved decisions: `D-01`, `D-02`, `D-06`, `D-07`, `D-08`.

## 11. Exclusions

Do not design or implement:

- Issue deletion.
- A user-facing change-history or activity-log section.
- Attachments or file-upload controls.
- AI-generated categorization or priority recommendations.
- Login, registration, or a complete authentication flow.
- Backend behavior, database integration, real authentication, or coded permission checks.
- Functional conditional logic or working form submissions in the prototype.
- Row selection, bulk actions, page-icon placeholders, or decorative squares.
- Additional product pages or features not defined by the canonical screen contracts.

Source references: `BR-10`, `BR-11`, `D-02`, `D-08`.

## 12. Acceptance Checklist

The Figma deliverable is ready for review when all applicable checks below are satisfied.

### Structure and fidelity

- One working page contains all canonical frames and supporting references.
- Canonical IDs are preserved exactly: `S-01`, `S-02-A`, `S-02-B`, `S-02-C`, `M-01`, `S-03`.
- The visual style is grayscale low-fidelity.
- Layers are editable, meaningfully named, and organized.
- Repeated elements use reusable local components.
- Auto Layout is used where appropriate.
- Explanatory notes and blockers remain outside product frames.
- No page-icon placeholders, decorative squares, row-selection controls, or bulk controls appear.

### Required content and behavior represented

- Issue list rows include ID, Title, Status, Priority, and Assignee when assigned.
- Issue details include all required fields, including Author and Created at.
- `M-01` includes required Title and Description fields and a Create action.
- A new issue is represented with status `Open`, priority `Not Set`, no assignee, author, creation timestamp, and a unique ID.
- Priority options are exactly `Low`, `Normal`, `High`, and `Critical`, with `Not Set` represented as an absent value rather than a selectable priority.
- Unauthorized assignment and priority controls remain visible but disabled.
- Status controls reflect both the actor's assignee relationship and permitted outgoing transitions.
- All four statuses and all four role/assignee contexts appear in the compact state reference.
- The status transition matrix matches Section 6 exactly.
- Important filtering matches Section 7, including High + Resolved being included and Critical + Closed being excluded.
- Empty and error examples listed in Section 8 are represented.
- Returning from `S-03` preserves the previously selected list tab.
- Successful assignment, priority, and status changes are annotated as remaining on `S-03`.

### Scope and unresolved decisions

- Prototype connections are annotations only; no functioning interaction logic is required.
- No backend, database, authentication, or coded permission enforcement is implemented.
- No unsupported behavior or copy is presented as approved.
- All unresolved decisions are visibly documented as blockers outside product frames: `B-01` through `B-06`.
- No unapproved UX decision is silently introduced as a finalized design rule.

Completion condition: Deliver the editable Figma-native design with the canonical screens, reusable components, compact state references, and annotated navigation intent. Keep every unresolved decision explicit. The brief does not authorize resolving those blockers by guessing.
